Depuis le 12 oct. 2026 (« grand passage »), le jeu de l'adresse principale est le nouveau jeu (`src2/` : village commun, héros RPG, donjons, raids, garnison) ; l'ancien jeu (`src/` : village nain 3D, raids contre les orques, ligue de médailles) reste jouable dans `docs/v1/`, ses villages gardés dans Firebase. ## Structure
- Site publié par GitHub Pages depuis `docs/` (`https://teodico-cloud.github.io/Mountain-Kings/`) :
  - `docs/index.html`, `game.js`, `sw.js`, `manifest.json` : le jeu actuel (généré par `tools/build2.py` depuis `src2/`). Service worker de portée `./`, caches `mk2-*` ; à son activation il efface aussi les caches `mk-*` (l'ancien jeu du temps où il était à la racine). Enregistré seulement une fois les modèles 3D chargés (`window.__mkSW`, ou au bout de 25 s) pour ne pas ralentir le premier chargement.
  - `docs/v1/` : l'ancien jeu (généré par `tools/build.py` depuis `src/`), son propre service worker (portée `v1/`, caches `mk1-*`, il n'efface que les siens), manifeste « Mountain Kings (ancien jeu) ». Chemins vers les fichiers communs en `../` (remplacés au build : `loadModels('../models/'`, `../thumbs/`).
  - `docs/v2/` : l'ancienne adresse d'essai. `index.html` renvoie vers `../` en gardant `?join=…` (anciens liens d'invitation) et désinscrit l'ancien service worker de `v2/` ; `sw.js` se désinscrit tout seul. `docs/v2/models/` : les modèles Meshy du jeu actuel (restent là).
  - Communs aux deux jeux : `docs/lib` (three.js r128), `docs/models` (KayKit), `docs/icons` (fabriquées par `build.py`), `docs/thumbs` (ancien jeu).
- Ancien jeu (`src/`), concaténé dans cet ordre en un seul `docs/v1/game.js` (IIFE) :
  - `p0_fb.js` : adaptateur Firebase (Realtime Database + Google Auth) qui imite l'API `db`/`room` des artefacts Claude ; `IMPORT_V` = village repris de l'ancienne version (`import_village.json`).
  - `p2_rules.js` : règles, simulation hors ligne déterministe, moteur de combat (10 Hz).
  - `p3_render.js` : rendu three.js r128 (caméra isométrique, modèles KayKit dans `docs/models/`).
  - `p5_audio.js` : musique (taverne) et bruitages, tout synthétisé en WebAudio (`SND`).
  - `p4_app.js` : interface, sauvegarde, protocole du raid à deux, tutoriel, aide, démarrage.
  - `p1_head.html` : CSS + squelette HTML.
  Ordre de concaténation : p0, p2, p3, p5, p4.
- `tools/build.py` : l'ancien jeu → `docs/v1/` (`index.html`, `game.js`, `sw.js`, `manifest.json`), plus les icônes communes `docs/icons` et `database.rules.json`. `--test` construit dans `.test/v1/`.
- `tools/fakeserver.py` + `tools/fakefb.js` : faux Firebase pour tester en local. Les builds `--test` vont dans `.test/` (ignoré par git, même disposition que `docs/`, liens vers docs/lib, models, icons, thumbs, v2/models) : jeu actuel à `http://127.0.0.1:PORT/`, ancien jeu à `/v1/` (`python3 tools/build.py --test`, puis `tools/test_ui.py`, `tools/test_duo.py`, `tools/test_gate.py`). Le build de test expose `window.__mk` pour les essais. Avec le rendu logiciel (swiftshader) ces essais sont lents (≈ 10 min pour `test_ui`, 15 min pour `test_duo`) : les lancer en arrière-plan avec `python3 -u` et un fichier de log. `tools/test_prod.py` : les pages de production (racine, `v1/`, renvoi de `v2/`) s'ouvrent sans erreur.
- `tools/test_engine.js` : essais du moteur (remparts, chemins, héros) avec node.
- `tools/make_thumbs.py` : vignettes `docs/thumbs/*.png` rendues depuis les modèles 3D (à relancer si les modèles changent).
- `tools/models_pipeline.py` : conversion des modèles KayKit (CC0) vers `docs/models/`.
- `tools/meshy_import.py` : allège un GLB Meshy (1-2 millions de triangles, textures 4K, 60-90 Mo) pour le téléphone → `docs/v2/models/`. Textures : couleur 1024, relief 512, métal/rugosité 256. Simplification par `gltfpack` (meshoptimizer, compilé depuis GitHub : `git clone https://github.com/zeux/meshoptimizer && make config=release gltfpack`, puis `GLTFPACK=…/build/release/gltfpack`), JAMAIS en mode agressif (`-sa`) : il casse les textures (atlas très fragmentés). Le simplificateur s'arrête seul à la limite qui garde les textures (≈ 36 000 triangles pour la taverne, 15 000 pour un personnage). Les personnages doivent être animés dans Meshy (Rig + Animate) : sans squelette, ils glissent comme des statues.
- Jeu actuel (refonte) : sources dans `src2/` (mêmes parties p0…p5), construit par `tools/build2.py` dans `docs/` (adresse principale ; chemins des modèles posés par la page : `window.MK_PATHS = { models: 'models/', m2: 'v2/models/' }`). Ses modèles Meshy sont dans `docs/v2/models/` (liste `M2_NAMES` dans `src2/p3_render.js` ; seuls ceux-là sont mis en cache par le service worker ; chargés après les modèles KayKit, un par un, la halle d'abord : le village s'affiche sans les attendre). Modèles en place : `taverne`, `halle`, `chantier` (affiché pour tout bâtiment de taille 2+ en construction). Un nouveau modèle de bâtiment : `meshy_import.py` → `docs/v2/models/<type>.glb`, ajouter le type à `M2_NAMES`, vérifier sous 4 angles (avant = +Z, tourné de 45° face à la caméra du jeu). Données Firebase sous `v2/` (users, invites, villages, presence, seats, live) ; règles v2 dans `tools/rules.py`, écrites dans le même `database.rules.json` ; pour rejoindre un village, la 2e personne réserve d'abord sa place (`v2/seats/<vid>` = son uid, écrit par `joinVillage`) puis s'inscrit dans `members` (les règles RTDB n'ont pas de `numChildren`). Village commun modifié par transactions RTDB + simulation minute par minute déterministe (heure du serveur).
- `python3 tools/build2.py --test` construit dans `.test/` (le site publié n'est jamais sali par un essai) ; les essais navigateur du jeu actuel ouvrent `http://127.0.0.1:PORT/`.
- `tools/test_v2.js` : essais des règles du nouveau jeu (node). `tools/test_v2_ui.py` : essai à deux joueurs dans le navigateur (fonder, héros, inviter, rejoindre, actions simultanées, absence de 2 jours) ; ≈ 10-15 min, en arrière-plan avec un log ; ne pas lancer d'autre Chromium en même temps (rendu logiciel très lent avec les modèles Meshy : un clic peut prendre 20 s).
- Donjons du nouveau jeu : `src2/p2d_donjon.js` (fabrication à partir d'une graine + combat pur à 20 pas/s : `genDungeon`, `djStart`, `djStep(st, {hid: {mx, my, sk, pot}})`, `djResult`), `src2/p4d_donjon.js` (menu Donjon, joystick, boutons, bilan ; clavier : flèches/ZQSD, 1-3, 4, espace/5 = roulade), rendu dans `p3_render.js` (`V3.dj.enter/sync/fx/exit`, décor en formes simples). Ordre de concaténation de build2 : p0, p2, p2d, p3, p5, p4d, p4. Retour au village par l'action `djEnd` (expérience, niveaux, points, butin plafonné par les réserves, niveau suivant `hero.dj`, prisonnier → candidat `pris: 1`), points de compétence `skill` (`hero.sk = {s0, s1, s2}`, rang 1 à 5), spécialisation `spec` (niveau 10). Essais : `node tools/test_donjon.js [--long]` (un robot joue chaque classe aux niveaux 1, 5, 10, la crypte, les Profondeurs et le jeu à deux ; ≈ 3-6 min de robot par donjon), `tools/test_v2_dj.py` (navigateur, ≈ 5 min), `tools/test_v2_prof.py` (navigateur, solo : menu, crypte, Profondeurs ; ≈ 6-8 min) et `tools/test_v2_profduo.py` (Profondeurs à deux ; ≈ 15-20 min).

## Règles
- Ne jamais committer un build `--test` (vérifier que `docs/index.html` et `docs/v1/index.html` chargent gstatic firebasejs, pas `fakefb.js` ; les builds `--test` vont dans `.test/`).
- Le dépôt et le site sont publics : seulement des prénoms (Téo, Lilou, Sukhoï), jamais de nom de famille, de date de naissance, d'adresse ou d'autre donnée personnelle dans le code, les notes ou les commits.
- Une sauvegarde de village doit rester compatible (`VERSION` dans `p2_rules.js`) : les joueurs ont des données réelles dans Firebase.
- Les règles RTDB dans `database.rules.json` sont collées à la main par Téo dans la console Firebase : le prévenir si elles changent.
- Tout changement du combat ou des messages du raid à deux : incrémenter `APP_PV` (p2_rules.js) dans l'ancien jeu, `DJ_PV` (src2/p2d_donjon.js) dans le nouveau (6 depuis la mission de la Source du Mal). Les deux joueurs doivent avoir la même version pour jouer ensemble.
- Remparts (ancien jeu) : bâtiments `rempart` de taille 1 dans `v.b` (pose et amélioration instantanées). Héros : `v.heroes[k] = {lvl, rest, up}`. Nouveau jeu : palissades et portes aussi dans `v.b` (`rempart`, `porte`), avec leur solidité `b.hp`.
